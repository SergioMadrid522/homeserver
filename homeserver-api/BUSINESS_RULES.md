# HomeServer V1 — Business Rules

## 1. Users

* Every user must have a unique email address.
* Passwords must never be stored as plain text. Only password hashes are stored.
* New users receive the `CLIENT` role by default.
* Users cannot select their own role during registration.
* Only an administrator can assign or modify user roles.
* Every user has a default storage limit of 150 GB.
* An administrator can modify the storage limit for a specific user.
* Storage values are stored in bytes.
* A disabled or deleted user must not be allowed to access the system.
* The server identifies the authenticated user through their session or access token.
* The frontend must not decide which user owns a resource.

## 2. Authentication

* Users authenticate using their email address and password.
* After successful authentication, the server creates a session or access token that identifies the user.
* Every protected request must include a valid session or token.
* The backend obtains the user ID from the authenticated session or token.
* The frontend must not send an arbitrary user ID to request files or folders.
* Logout invalidates or removes the active session or token.

## 3. Files

* Every file belongs to exactly one user.
* A file can belong to zero or one folder.
* A file with no folder is located in the user's Home directory.
* The visible file name includes its extension, for example `report.pdf`.
* Two files with the same name cannot exist inside the same folder.
* Files with the same name can exist in different folders.
* The file name shown to the user is different from the name used to store the physical file.
* Every physical file must have a unique `storageName`.
* The `storageName` is generated by the backend and is never selected by the user.
* The MIME type and file size are obtained from the uploaded file by the backend.
* The frontend must not be trusted to provide the real MIME type or size.
* File sizes are stored in bytes.
* Every file has a SHA-256 checksum.
* The checksum is used to verify file integrity and identify identical content.
* The checksum is not used as the physical storage name.
* A file may have the same checksum as another file located in a different folder.
* A file can be marked as a favorite.
* Renaming a file changes only its visible name.
* Renaming a file does not change its physical storage name.
* Moving a file changes its `folderId`.
* Moving a file to Home sets its `folderId` to `null`.

## 4. File Storage

* Physical files are stored on the server's HDD.
* PostgreSQL stores file metadata, not the file content.
* The database stores the relationship between the visible file and its physical storage name.
* When listing files, the backend reads metadata from PostgreSQL.
* The HDD is accessed only when the file content is required, such as during download.
* Before returning a file, the backend must verify that it belongs to the authenticated user.
* The backend uses `storageName` to locate the physical file on the HDD.
* The downloaded file must use the visible `name`, not the physical `storageName`.

## 5. Folders

* Every folder belongs to exactly one user.
* A folder can have zero or one parent folder.
* A folder with no parent is located in the user's Home directory.
* A folder can contain multiple files.
* A folder can contain multiple child folders.
* A folder cannot be its own parent.
* A folder must not be moved inside itself or inside one of its descendants.
* Two folders with the same title cannot exist inside the same parent folder.
* Folders with the same title can exist under different parent folders.
* Folder paths are not stored in the database.
* The backend reconstructs a folder path by following the parent-folder hierarchy.
* Renaming a folder changes only that folder's title.
* Renaming a folder does not require updating its descendants.
* Moving a folder changes only its `parentFolderId`.
* Moving a folder to Home sets its `parentFolderId` to `null`.
* Every folder has a color.
* New folders use `#6EA8FE` as their default color.
* A folder can be marked as a favorite.

## 6. Home Directory

* Home is not stored as a physical folder record.
* A file is located in Home when its `folderId` is `null`.
* A folder is located in Home when its `parentFolderId` is `null`.
* To display Home, the backend returns:

  * Active files owned by the authenticated user whose `folderId` is `null`.
  * Active folders owned by the authenticated user whose `parentFolderId` is `null`.

## 7. Navigation

* Frontend URLs and backend API URLs are independent.

* The frontend may display readable paths such as:

  `/home/Documents/School/Projects`

* The backend operates using folder IDs instead of visible paths.

* The frontend keeps the folder ID associated with every displayed folder.

* When a user opens a folder, the frontend sends its ID to the backend.

* The backend verifies that the requested folder belongs to the authenticated user.

* Breadcrumbs are generated by following each folder's parent until Home is reached.

## 8. Trash

* Files and folders use soft deletion before permanent deletion.
* Moving an item to Trash sets:

  * `isDeleted = true`
  * `deletedAt = current date and time`
* Moving an item to Trash does not immediately remove its physical content.
* Items in Trash continue consuming storage.
* A file or folder can only be permanently deleted when `isDeleted` is already `true`.
* Permanent deletion removes the physical file from the HDD.
* Permanent deletion removes the related database record or makes it permanently inaccessible.
* Permanent deletion reduces the user's current storage usage.
* Moving a folder to Trash also affects its descendant folders and files.
* The frontend must display a confirmation before moving a folder with content to Trash.
* The backend must enforce deletion rules even if the frontend confirmation is bypassed.
* Restoring an item sets:

  * `isDeleted = false`
  * `deletedAt = null`
* Because folder relationships are preserved, restored items return to their previous logical location.

## 9. Storage Usage

* `storageLimit`, `currentStorage`, and file `size` use bytes.

* New users receive a default limit of `150000000000` bytes (150 GB).

* New users start with `currentStorage = 0`.

* Before accepting an upload, the backend must verify:

  `currentStorage + uploadedFileSize <= storageLimit`

* When a file is successfully stored, its size is added to `currentStorage`.

* Moving a file to Trash does not reduce `currentStorage`.

* Permanently deleting a file subtracts its size from `currentStorage`.

* File creation and storage-counter updates should be performed atomically when possible.

* The system should provide a way to recalculate `currentStorage` from file metadata if the stored value becomes inconsistent.

## 10. Multiple Operations

* Multiple downloads are limited to 50 selected items per request.
* Multiple files are downloaded as a ZIP archive.
* Multiple folders are downloaded as a ZIP archive.
* The frontend must prevent selecting more than 50 items.
* The backend must independently reject requests containing more than 50 items.
* Every selected item must belong to the authenticated user.
* Permanent bulk deletion must only affect items already located in Trash.

## 11. Authorization and Security

* Every file and folder operation must verify ownership.
* Knowing a file or folder ID does not grant access to it.
* The backend must reject access to resources owned by another user.
* IDs received through route parameters or query parameters must be validated.
* The backend must not trust file names, MIME types, sizes, ownership information, or roles supplied by the client.
* PostgreSQL must not be exposed directly to the internet.
* Only the NestJS backend communicates with PostgreSQL.
* Physical storage paths and `storageName` values should not be exposed unnecessarily to the frontend.

## 12. V1 Scope

The first version includes:

* User registration and login.
* User-specific storage limits.
* File uploads.
* File downloads.
* Folder creation.
* File and folder navigation.
* File and folder renaming.
* Moving files and folders.
* Favorites.
* Trash and permanent deletion.
* Multiple downloads as ZIP files.
* Storage usage tracking.
* SHA-256 checksum generation.
* Locally hosted PostgreSQL, NestJS, Next.js, and HDD storage.

The first version does not include:

* File or folder sharing.
* Multiple owners for one resource.
* Public sharing links.
* Advanced resource permissions.
    - VIEWER: can view and download shared content.
    - EDITOR: can rename, move, and modify shared content.
    - UPLOADER: can upload new files but cannot permanently delete shared content.
    - MANAGER: can manage sharing settings and assign permissions.
    
* File version history.
* Physical-file deduplication.
